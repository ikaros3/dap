# 제1장 전사아키텍처 개요
## 제1절 전사아키텍처 정의
### 1. 전사아키텍처 개념
#### 가. 전사아키텍처 도입 배경
- 환경 변화에 민첩하게 대응하는 능력이 정보기술의 역할로 중요시됨
- 비즈니스 복잡도 증대, 업무와 IT 기능의 분리는 더 이상 무의미
- 시스템이 너무 복잡하여 환경 변화에 대응하려 해도 어디를 어떻게 변경해야 할지 모르는 상황
- 건축물의 설계도처럼 기업의 전체 시스템을 쉽게 파악할 수 있는 수단이 필요
  → 복잡한 기업 시스템을 파악하기 쉽게 정리하고, 필요한 형태로 변화시키는 것을 쉽게 하기 위해 **전사아키텍처** 도입
#### 나. 전사아키텍처 정의
- 기업의 목표와 요구를 잘 지원하기 위해 **IT 인프라의 각 부분들이 어떻게 구성되고 작동되어야 하는가를 체계적으로 기술**하는 것
- 복잡한 기업의 모습을 다양한 측면(비즈니스, 데이터, 애플리케이션, 기술 등)에서 분석·표현하여 이해하기 쉽도록 정보체계를 구축하고 활용하는 것
- 도입 목적 : **IT 투자 대비 효과 최대화**, 기업의 목적을 가장 잘 달성할 수 있는 방식으로 IT 인프라 구성
- 도입 효과 : 비즈니스와 IT의 유기적 연결, 비즈니스 환경 변화에 신속한 대응, IT 자체의 효율성 증대
- **미국 예산관리국(OMB)의 정의** (OMB 회람 A-130)
  - "조직 및 업무 활동과 정보기술 간의 관계를 **현재 모습과 향후 추구할 모습을 별도로 정의한 청사진**"
  - IT와 업무 간의 연계, 현재 모습과 미래 모습을 포함
  - 구성 : 업무 프로세스, 정보 흐름 및 관계, 애플리케이션, 데이터 명세 및 관계, 기술 하부 구조
  - 이후 실무적으로 네 영역으로 정리 : 비즈니스 아키텍처(업무 프로세스, 정보 흐름 및 관계), 애플리케이션 아키텍처, 데이터 아키텍처(데이터 명세 및 관계), 기술 아키텍처
- **미국 전자정부법의 정의**
  - "조직의 임무가 정의한 전략적 정보 자산, 그 임무 수행에 필요한 정보, 필요한 기술, 변화하는 요구에 대응하기 위한 신기술 구현의 전환 과정으로 구성. 각 구성 요소는 **현행 아키텍처, 목표 아키텍처, 전환을 위한 계획**을 포함"
  - 조직의 임무, 임무에 필요한 정보와 정보기술, 전환 계획을 명시하고 현행과 목표 아키텍처를 동시에 포함
- **대한민국 EA/ITA법의 EA 정의** (정보시스템의 효율적 도입 및 운영에 관한 법률, 2005년 12월 30일 공표)
  - "일정한 기준과 절차에 따라 업무, 응용, 데이터, 기술, 보안 등 조직 전체의 정보화 구성 요소들을 통합적으로 분석한 뒤 이들 간의 관계를 구조적으로 정리한 체계 및 이를 바탕으로 정보시스템을 효율적으로 구성하기 위한 방법"
  - 배경 : 정보시스템을 체계적으로 관리할 체제가 없어 중복 투자, 시스템 간 연계 미흡 등의 문제 발생
  - 전사아키텍처의 활용을 촉진하고 공공 기관 등에 정보시스템을 효율적으로 도입·운영할 기반 마련
- 전사아키텍처는 정보기술의 혁신 활동과 관리 통제를 포함하며, 도입·구축뿐 아니라 **운영과 평가까지 통합적으로 관리**하는 것
- 기업은 전사아키텍처를 통해 IT 자산을 평가하고 전사 관점에서 재설계·재배치하며, IT의 효율성과 투자 효과를 측정하는 기준으로 활용
#### 다. 전사 개념
- **전사(Enterprise)** : 일반적으로 기업 또는 기관을 지칭
  - "공동의 목표를 추구하기 위해 고객과 상품 또는 서비스가 존재하고 이를 지원하기 위한 조직, 자원, 기술을 보유하며 필요한 업무 프로세스를 수행하는 조직의 집합체"
  - 비즈니스의 변화 동인을 확인하고 전략을 정의할 수 있는 조직 단위이며, 비즈니스 활동 정보를 공유하는 조직 단위
[[img:G1-01]]
- 전사의 유형은 다양함
  - 전사가 하나의 기업이나 기관과 정확히 일치하지 않을 수 있음
  - 규모가 큰 기업은 여러 개의 전사로 구성될 수 있으며, 각 전사는 독립적인 운영 주체
  - 전사는 구분 가능한 다수의 사업 영역으로 구성
- 전사아키텍처 수립 시 **전사의 범위를 초기에 명확히 정의**하고 이해당사자들이 충분히 공감해야 함
  - 전사의 정의는 수립 과정의 중요한 판단 기준, 모든 활동은 정의된 전사의 성과와 목표에 초점
#### 라. 아키텍처 개념
- 고대 그리스어로 건축 혹은 석공명인(Master)을 의미하는 'Architecton'에서 유래 — 건축물의 골격을 제공하는 설계도 역할
- 산업시대에는 항공기, 자동차, 선박 등의 개발에, 오늘날에는 정보체계, 소프트웨어 내장형 체계, 지휘통제 통신체계 등의 구축에 적용
- **IEEE Std. 1971**의 정의 : "구성요소의 구조, 구성요소들 사이의 관계, 구성요소의 설계 그리고 시간 경과에 따른 구성요소의 발전을 위한 원리와 지침"
- 아키텍처는 대상의 구조뿐 아니라 유지 관리를 위한 원칙과 지침, 목표 아키텍처로 가기 위한 계획을 포함
[[img:G1-02]]
- **규칙(Rule) 관점**
  - 아키텍처의 일관성이 흔들리는 이유는 기술적 문제 이전에 관리적 문제일 수 있음
  - 상호운용이나 일관성 유지를 위해 준수해야 하는 원칙을 수립·적용함으로써 아키텍처의 연속적인 모습을 관리
- **모델(Model) 관점**
  - 구체적인 모델이나 기법으로 분석된 후 그 결과를 정의된 표기법으로 표현
  - 아키텍처 모델은 담당자 간에 공유되어야 하는 매우 중요한 정보
  - 수립 시뿐 아니라 향후 변경을 고려한 절차나 기법의 표준화가 중요
- **계획(Plan) 관점**
  - 현재 아키텍처와 목표 아키텍처를 정의하고, 현재 상태에서 목표 상태로 가기 위한 이행 전략과 구축 계획이 필요
  - 계획 = 전사아키텍처의 이행 전략과 이행 계획
- 아키텍처 = 목적에 따라 복잡한 대상을 단순하게 표현하고, 구성요소의 변화 요구를 수용할 수 있게 한 **청사진(Blueprint)**
- 다시 정의하면, 전사아키텍처란 **전사에 대한 아키텍처를 정의·관리하여 전사의 비즈니스 목표를 위해 아키텍처 정보를 활용하여 IT 인프라를 최적으로 구성하는 것**
### 2. 전사아키텍처 추진 현황
- 정부기관과 민간기업의 IT 혁신을 위한 주된 관심사, 특히 정부기관은 전자정부 구현 사업으로 활발히 추진
- **2005년 12월** 공공 부문에 전사아키텍처 도입을 의무화하는 "정보시스템의 효율적 도입 및 운영 등에 관한 법률" 제정
  → **2007년부터** 단계적으로 추진
> **[Tip] 전사아키텍처(EA)와 정보기술아키텍처(ITA)**
> 1996년 미국 정보기술관리혁신법에서 ITA(Information Technology Architecture)라는 용어를 사용했으나, 2000년 OMB A-130 회람에서 이 개념을 전사아키텍처(Enterprise Architecture)라 명명함
> 전사아키텍처는 광의의 아키텍처 개념, 정보기술아키텍처는 정보기술 중심의 아키텍처 개념. 국내는 ITA를 먼저 사용했으나 현재는 EA로 통합해 사용 (이 책에서는 특별히 구분하지 않음)
- EA/ITA법의 주요 내용 (의무 도입 기관)
  - 범정부 아키텍처 목표를 지원하고 각 기관의 목표에 맞는 도입 계획을 수립·제출
  - 아키텍처 추진 조직 구성, 추진 인력의 역량 강화를 위한 교육 추진
  - 도입 계획에 따라 아키텍처를 도입·운영하고 지속적으로 유지·발전
  - 범정부 차원의 공동 활용을 위해 전사아키텍처 관련 정보 제공
  - **아키텍처 성숙도 모델**로 도입·운영 실태 및 추진 성과 분석
  - 정보화 사업 추진 시 기술 지침 및 상호 운용성 확보 등을 위한 기술 평가 수행
[[img:G1-03]]
- 행정안전부와 한국정보화진흥원이 공공 기관 전사아키텍처 추진의 주관 부처
  - 범정부 차원의 일관성 확보, 공공 기관 아키텍처 정보의 종합적 분석·활용을 위해 **참조 모델, 산출물 메타 모델, 지침** 등을 개발·보급

| **범정부 전사아키텍처 성숙도 모델** | - 아키텍처 수준 및 향후 발전 방향을 수립할 수 있도록 1~5단계의 아키텍처 수준과 측정 항목을 정의한 모델¶- 매년 추진 실태와 함께 성숙도를 측정해야 함 |
| **범정부 전사아키텍처 지원 시스템(GITAMS)** | - 아키텍처 관련 표준과 기준 등을 제공하고, 각 기관의 아키텍처 정보를 공유·활용할 수 있도록 지원하는 시스템¶- 각 기관은 필수 산출물에 해당하는 정보를 매년 GITAMS에 등록해야 함 |
### 3. 전사아키텍처 관련 데이터아키텍처 전문가 역할
- 고품질의 데이터 모델 또는 데이터아키텍처를 정의하려면 전사아키텍처의 개념을 충분히 이해해야 함
- 전사아키텍처 수립 프로젝트에서 데이터아키텍처 전문가는 **데이터아키텍처 영역을 직접 수행하거나 간접적으로 관여**
- 소속 기업의 전사아키텍처 추진 내역에 관심을 갖고 구축된 전사아키텍처 정보를 적극 활용
- 전사아키텍처를 구축하지 않은 기업이라면 데이터아키텍처 영역만이라도 전사아키텍처 개념으로 접근 가능
## 제2절 전사아키텍처 프레임워크
### 1. 전사아키텍처 프레임워크 개념
- 전사아키텍처를 어떻게 표현하고 운영할 것인가에 대한 전체적인 사고의 틀
- **전사아키텍처 활동에서 얻어지는 산출물을 분류하고 조직화하고 유지 관리하기 위한 전체적인 틀**을 정의하는 것
- 전사아키텍처 수립을 위해 먼저 프레임워크를 정의해야 함
  - 선진 모델과 정부 가이드를 참조할 수 있으나, 무조건 적용하기보다 **기업의 특성에 맞게** 정의
### 2. 전사아키텍처 프레임워크 구성
- 국내에서 비교적 일반적으로 적용되는 프레임워크 사례 기준
- 3가지 영역으로 구분
  - **전사아키텍처 정책** : 전사아키텍처 수립을 어떻게 할 것인가의 방향 — 아키텍처 매트릭스, 전사아키텍처 비전, 전사아키텍처 원칙
  - **전사아키텍처 정보** : 구축하는 전사아키텍처 정보의 구체적인 모습 — 현행 아키텍처, 목표 아키텍처, 이행 계획
  - **전사아키텍처 관리** : 구축된 전사아키텍처의 관리·활용 방법 — 관리 체계, 관리 시스템, 평가 모형

#### 가. 전사아키텍처 정책
- 전사아키텍처 구축 목적과 방향을 먼저 정의
  - 정보를 어떻게 구성할 것인지, 달성하고자 하는 궁극적인 모습은 무엇인지, 효과적인 관리·활용 원칙은 무엇인지
- **아키텍처 매트릭스**
  - 전사아키텍처 정보를 체계적으로 분류한 틀
  - 기업이 관리하려는 **전사아키텍처 정보의 수준과 활용 계층을 결정**하는 수단

‖ 뷰(View) / 관점(Perspective) | 비즈니스 아키텍처 | 애플리케이션 아키텍처 | 데이터 아키텍처 | 기술 아키텍처 |

| ^^ | - 전사 사업 모델¶- 조직 모델¶- 비즈니스 전략 | - 전사 애플리케이션 영역 모델¶- 애플리케이션 원칙 | - 전사 데이터 영역 모델¶- 데이터 원칙 | - 전사 기술 영역 모델¶- 기술 참조 모델 |
| **책임자/분석자**¶(개념적) | 업무의 세부 구성 정보와 업무/조직 간 관계 정보 | 상위 수준의 기능 구성 정보와 응용시스템 간 관계 정보 | 데이터베이스에서 관리되는 주요 데이터 개체와 개체 간 관계 | 정보 기술 기반 자원의 유형별 구성과 인터페이스 정보 |
| ^^ | - 업무 기능 모델 | - 애플리케이션 모델¶- 애플리케이션 표준 | - 개념 데이터 모델¶- 데이터 표준 | - 표준 프로파일 |
| **설계자**¶(논리적) | 업무의 연계성, 흐름 정보 | 응용 시스템의 상세한 기능 정보와 물리적 분산 정보 | 데이터베이스의 논리적 데이터 구조 | 기술 기반 자원의 도입과 운영을 위한 유형별 구조 및 관리 체계 정보 |
| ^^ | - 프로세스 모델 | - 컴포넌트 모델 | - 논리 데이터 모델 | - 기술아키텍처 모델 |
| **개발자**¶(물리적) | 업무 수행을 위한 구체적 절차, 양식, 업무 관계 정보 | 프로그램의 물리적인 구성 체계와 각 프로그램 구현 정보 | 데이터베이스의 물리적 구조 정보 | 도입된 기술 기반 자원의 도입, 운영, 관리에 관한 구체적 정보 |
| ^^ | - 업무 매뉴얼 | - 프로그램 목록 | - 물리 데이터 모델¶- 데이터베이스 객체 | - 기술 자원 목록¶- 제품 목록 |
  - 일반적으로 **뷰와 관점**의 두 차원으로 정보를 구분하고, 교차하는 각 셀에 전사아키텍처 정보의 실체가 되는 **산출물**을 정의
  - 좌우로 바라보는 것 = **뷰(View)** : 비즈니스, 애플리케이션, 데이터, 기술
  - 위에서 아래로 바라보는 것 = **관점(Perspective)** : 계획자, 책임자(분석자), 설계자, 개발자
  - 각 셀은 전후좌우의 셀과 연관성을 가지며, **셀 간의 추적성**이 확보되어야 함
- **전사아키텍처 비전**
  - 전사아키텍처 수립을 통해 기업이 궁극적으로 달성하고자 하는 모습
  - 구축의 목표와, 목표를 효과적으로 달성하기 위한 전략과 방향을 포함
- **전사아키텍처 원칙**
  - 전사아키텍처 정보를 효율적으로 구축하고 효과적으로 활용하기 위해 **조직 구성원이 공유해야 할 규범**
  - 전사아키텍처 대원칙, 아키텍처 원칙, 표준 등을 포함
#### 나. 전사아키텍처 정보
- 아키텍처 매트릭스에서 정의한 각 산출물에 대해 현재 상태와 목표 상태의 정보를 구축하고, 목표 달성을 위한 이행 계획 수립
- **아키텍처 도메인(Architecture Domain)** : 아키텍처 정보의 영역을 구분한 것 — 아키텍처 매트릭스 상에서 **뷰의 관점**으로 영역을 구분한 것
  - 현행 아키텍처와 목표 아키텍처는 아키텍처 도메인별로 구축
[[img:G1-05]]
- **현행 아키텍처** : 도메인별로 정의된 산출물에 대해 기업의 현재 상태를 아키텍처 정보로 정의한 것
- **목표 아키텍처** : 도메인별로 정의된 산출물에 대해 기업이 궁극적으로 달성하고자 하는 상태를 아키텍처 정보로 정의한 것
- **전사아키텍처 이행 계획** : 도메인별로 현재 모습에서 목표 모습으로 이행하기 위한 이행 전략과 이행 계획을 정의한 것
> **[Tip] 비즈니스·업무·사업, 애플리케이션·응용**
> 'Business'는 '사업' 또는 '업무'로 번역됨. 사업은 전사 차원의 경영, 업무는 실무 차원의 활동 어감이 강하며 비즈니스는 둘을 포괄함 (이 책에서는 구분하지 않으나 정부 참조 모델에서는 '업무'를 그대로 씀)
> 'Application'은 '응용'과 같은 의미. 업계에서 많이 쓰는 '애플리케이션'을 쓰되 정부 참조 모델에서는 '응용'을 그대로 씀
- 아키텍처 도메인의 일반적 구분
  - **비즈니스아키텍처** : 조직의 목적 및 임무를 지원하기 위해 수행하는 업무를 분석하고 업무 활동 단위로 분할하여 표현
  - **데이터아키텍처** : 업무 처리 및 의사결정을 위해 어떤 정보가 사용·전달되어야 하는지 표현 — 전사 데이터 구성을 분류하고 데이터 모델을 정의
  - **애플리케이션아키텍처** : 임무 수행에 필요한 애플리케이션의 기능 및 관계를 정의 — 애플리케이션 단위를 분류하고 애플리케이션 간 인터페이스를 정의
  - **기술아키텍처** : 위 세 아키텍처를 지원하는 정보 기술 인프라 요소 및 구조와 관계를 표현 — 기술 영역을 분류하고 표준 프로파일과 기술 아키텍처 모델을 정의
#### 다. 전사아키텍처 관리
- 전사아키텍처 정보의 지속적인 유지 관리와 효과적 활용을 위해 관리 체계 정립과 관리 시스템 구축이 필요하며, 지속적인 평가·개선 필요
- **전사아키텍처 관리 체계** ('전사아키텍처 거버넌스')
  - 구축된 전사아키텍처를 유지·개선하기 위한 **제도적 기반**을 수립하는 것
  - 전사아키텍처 원칙을 준수하도록 확인·통제하기 위한 조직과 프로세스 정의 포함
  - 목적 : 전사아키텍처 활동 관리, 정보 변경 통제, IT 프로젝트가 기본 원칙과 정책을 준수하도록 함
- **전사아키텍처 관리 시스템**
  - 정보 관리의 효율성을 제고하고 정보 공유를 활성화하기 위해 구축하는 정보시스템
  - 일반적 구성 : 정보를 정의하는 **모델링 도구**, 정보를 저장하는 **리포지터리**, 정보를 배포하는 **포털**
- **전사아키텍처 평가**
  - 주기적으로 평가하고 개선점을 도출하여 반영
  - 수준을 객관적·정확하게 평가할 수 있는 **전사아키텍처 성숙 모형**이 필요
### 3. 아키텍처 도메인 구성
- 아키텍처 도메인의 구성은 기업이 아키텍처 매트릭스를 어떻게 정의하느냐에 따라 다름
- 국내 기업에서 비교적 일반적인 도메인별 구성 내역 ([표 1-1-2] 아키텍처 매트릭스 기준)
[[img:G1-06]]
- 정보기술은 철저하게 비즈니스 전략과 연계되어야 함
  - 데이터아키텍처는 비즈니스아키텍처에서 정의한 업무를 지원하는 데이터를, 애플리케이션아키텍처는 업무 수행에 필요한 애플리케이션을 정의
  - 기술아키텍처는 데이터 및 애플리케이션아키텍처를 잘 지원하기 위한 기술적 특성을 감안하여 정의
#### 가. 비즈니스아키텍처
- **전사 사업 모델 (계획자 관점)**
  - 아키텍처 정보를 구축하는 대상인 전사(Enterprise)의 범위를 정의하는 것에서 시작
  - 내외부 이해관계자 분석, 외부 객체와의 가치사슬 분석으로 전사를 정의
  - 어떤 기능이 외부 객체에 의해 수행되고, 외부 객체의 어떤 기능을 전사 내부가 수행하는지 분석
[[img:G1-07]]
- **조직 모델 (계획자 관점)**
  - 기업의 사업 모델을 지원하기 위한 조직 구조를 정의
  - 비즈니스 수행 지리적 위치와 내부 객체를 도출하여 조직 구조와 업무 분장 정의
- **업무 기능 모델 (책임자 관점)**
  - 업무 기능을 계층적으로 분할하고 기능 내용을 정의
  - 분할 기준은 **조직이 아닌 업무 기능의 유사성과 연관성**
  - 상위 업무 기능은 하위 업무 기능의 합으로 완전히 표현될 수 있어야 함
  - 데이터, 애플리케이션과의 상호 비교를 통한 연관 분석이 이루어짐
- **프로세스 모델 (설계자 관점)**
  - 업무 기능을 상세화하여 프로세스를 계층적으로 분할하고 활동 내용을 정의
  - 프로세스 : 업무 수행을 위해 정보를 입력 받아 의미 있는 활동을 통해 산출물을 생성하는 일련의 과정
  - 데이터, 애플리케이션과의 연관 분석이 반복적으로 이루어짐
- **업무 매뉴얼 (개발자 관점)**
  - 업무 기능이나 프로세스별 업무 내역을 상세히 기술한 자료, 전사아키텍처에서는 **목록 수준**의 정보를 관리
#### 나. 애플리케이션아키텍처
- 업무를 지원하는 전체 애플리케이션을 식별하고 연관성을 정의하며, 업무와 IT 특성을 고려해 그룹화·범주화하여 전체 구조를 체계화
- 애플리케이션 서비스는 지원 업무와 데이터 특성을 고려해 정의하고, 서비스 간 상호 연관관계를 분석·정의
  → 향후 애플리케이션의 배치, 통합, 포트폴리오 관리를 위한 시각 제공
- **전사 애플리케이션 영역 모델 (계획자 관점)**
  - 애플리케이션을 식별하고 특성 분석을 통해 전사 수준에서 구조화
  - 독립 구현·운영될 수 있는 애플리케이션을 정의하고, 관련 업무, 데이터와 IT 특성을 감안해 그룹화하여 애플리케이션 영역 정의
- **애플리케이션 모델 (책임자 관점)**
  - 각 애플리케이션이 지원하는 기능과 데이터 정보를 정의하고 제공 서비스를 도출하며 연관 관계 정의
  - 어느 업무 프로세스에서 활용되고 어떤 정보를 생산·관리하는지 연관성 분석
  - 정의 방식은 **개발 방법론에 의존적**
- **컴포넌트 모델, 클래스 모델 (설계자 관점)**
  - 실제 개발에 필요한 설계 정보 관리 — 컴포넌트 정의, 클래스 정의, 데이터 흐름도(DFD) 등
  - 기업의 개발 방법론에 영향을 많이 받음 (예: 정보계는 CBD 방법론, 운영계는 메인프레임 중심의 구조적 방법론)
- **프로그램 목록 (개발자 관점)**
  - 애플리케이션의 최종 단위인 프로그램에 대한 정보 관리
#### 다. 데이터아키텍처
- 업무 수행에 필요한 **데이터의 구조를 체계적으로 정의**하는 것
- 전사의 데이터 영역을 분류 — 업무 데이터와 메타 데이터 구분, 업무 데이터는 운영계·정보계 데이터 등으로 구분
- 이를 기준으로 전사 수준의 주제 영역 모델, 개념 데이터 모델을 정의하고, 영역별로 논리·물리 데이터 모델 정의
- 데이터아키텍처 전문가가 다루는 범위는 데이터 구조뿐 아니라 **데이터 표준, 데이터 관리 체계 등을 포함하는 광의의 데이터아키텍처**
- **전사 데이터 영역 모델 (계획자 관점)**
  - **개괄 데이터 모델**이라고도 하며, 상위 수준의 전사 데이터 영역을 분류하여 표현 — 상위 주제 영역 수준의 데이터 구성도
  - 주제 영역 : 업무 기능과 대응되는 개념으로 유사 데이터를 그룹화한 것
- **개념 데이터 모델 (책임자 관점)**
  - 전사 수준의 데이터 모델로 **단위 주제 영역 또는 핵심 엔터티** 정도를 표현
  - 전사 수준의 데이터를 전체적으로 표현하는 기본 틀, 전사 데이터아키텍처 관리에 매우 유용
  - 핵심 엔터티는 일반적으로 단위 주제 영역별로 한두 개 정도 도출
- **논리 데이터 모델 (설계자 관점)**
  - 개념 데이터 모델의 주제 영역과 핵심 엔터티를 기본으로 업무 요건을 충족하는 데이터의 상세 구조를 논리적으로 구체화
  - 필요한 모든 엔터티를 도출하고 식별자, 속성, 관계, 서브타입 등을 정의
  - 엔터티, 속성의 명칭, 정의, 형식, 규칙, 코드 등을 **전사적 표준**으로 정의·관리해야 함
- **물리 데이터 모델 (개발자 관점)**
  - 기술적 환경과 특성을 고려해 물리적 데이터 구조를 설계하고 데이터베이스 객체를 정의
  - 논리 모델을 물리 구조로 전환하고 데이터 무결성을 보완, 데이터 분산 설계에 따른 추가 무결성 규칙 정의
  - 성능을 고려해 인덱스 설계, 비정규화 수행
#### 라. 기술아키텍처
- 비즈니스, 데이터, 애플리케이션 아키텍처의 요건을 지원하는 **전사의 기술 인프라 체계**를 정의
  - 기술 인프라 : 하드웨어, 시스템 소프트웨어, 통신 네트워크, 시스템 개발도구, 시스템 관리도구, 최종 사용자 소프트웨어 등
- 기술 참조 모델과 표준 프로파일 구축 효과 : 이식성·확장성 강화, **벤더 독립성** 확보, 시스템 간 상호운용성 강화
- 다른 아키텍처와 달리 **개별 기업에서도 기술 참조 모델을 정의하는 것이 일반적** (아키텍처 매트릭스에서 기술 참조 모델을 계획자 수준 산출물에 포함한 이유)
- **전사 기술 영역 모델, 기술 참조 모델 (계획자 관점)**
  - 전사 기술 영역 모델 : 업무 활동에 필요한 정보기술의 영역을 상위 수준에서 분류
  - 기술 참조 모델(TRM) : 필요한 정보기술을 상위 수준에서 논리적으로 분류한 틀, 전사 기술 영역 모델과 같은 범주
  - 기술 참조 모델은 **일반적인 표준을 최대한 수렴해 정의**하는 것이 특징
[[img:G1-08]]
- **표준 프로파일 (책임자 관점)**
  - 표준 프로파일(SP) : 기술 참조 모델에 명시된 서비스를 지원하기 위한 **정보기술 표준들의 집합**
  - 모든 기술 아키텍처 요소에 영향을 미치는 표준 포함 → 이식성, 확장성, 상호운용성, 호환성 제고
  - 일반적으로 기술 표준을 프로파일 대상으로 하며, 최근에는 **제품**도 포함하는 추세
- **기술 아키텍처 모델 (설계자 관점)**
  - 서비스 카테고리별 아키텍처 패턴 정의, 소프트웨어·하드웨어·네트워크 구성 요소의 배치도 정의
- **기술 자원 목록, 제품 목록 (개발자 관점)**
  - 표준 프로파일이나 기술 아키텍처별 관련 기술 자원 목록, 제품 목록을 관리
### 4. 전사아키텍처 프레임워크 사례

## 제3절 전사아키텍처 참조 모델
### 1. 참조 모델 정의
#### 가. 참조 모델 개념
- **참조 모델(Reference Model)** : 아키텍처 구성 요소를 식별하여 표준화한 것으로, 전사아키텍처 수립 시 참조하는 **추상화된 모델**
  - 다양한 관점을 충족하도록 시스템의 개념적 모델을 추상화하고, 구성 요소를 재사용 가능한 방식으로 만들어 여러 기업이 사용할 수 있도록 한 것
- 비슷한 특성의 산업군마다 정의된 참조 모델 활용을 추천 — 동종 참조 모델을 참조해 고유의 아키텍처 구성 (잘 알려진 것 : 국방, 공공 참조 모델)
- 아키텍처별 참조 모델
  - 업무 참조 모델(BRM, Business Reference Model)
  - 데이터 참조 모델(DRM, Data Reference Model)
  - 서비스 참조 모델(SRM, Service Reference Model)
  - 기술 참조 모델(TRM, Technical Reference Model)
  - 성과 참조 모델(PRM, Performance Reference Model)
#### 나. 참조 모델 현황
- 정부는 업무, 서비스, 기술, 데이터, 성과 참조 모델 등 **5가지 참조 모델** 정의 추진
[[img:G1-15]]
[그림 1-1-9] 범정부 EA 참조 모델 개념 구조
- **성과 참조 모델** : 정보화 성과 측정을 위한 항목과 지표 및 방법 제시
- **업무 참조 모델** : 업무아키텍처의 기준, 대상 기관의 사업 또는 업무를 전체적으로 분류·정의
- **서비스 참조 모델** : 응용아키텍처의 기준, 응용 서비스의 기능을 분류·정의
- **데이터 참조 모델** : 데이터아키텍처의 기준, 기관 간 교환되는 주요 데이터 요소를 분석·정의하고 표준화
- **기술 참조 모델** : 기술아키텍처의 기준, 정보기술을 분류 및 식별
- **범정부 참조 모델**
  - 전사적 아키텍처의 **일관성, 재사용성, 상호 운용성** 확보를 위해 정보화 구성 요소의 표준화된 분류 체계와 형식을 정의
  - 일반 기업 프로젝트와 달리 범정부 정보화 사업을 체계적으로 추진할 수 있는 참조 모델과 지침을 만들어 보급하는 데 역점
- 참조 모델은 **미 연방정부 전사아키텍처(FEA)**에서 처음 제시된 개념
  - 미 예산관리국이 2002년부터 기관 간 업무 프로세스를 단순화·통합하기 위해 FEA 개발 시작
  - 각 기관 전사아키텍처 구축을 위한 '기준'으로 영역별 참조 모델 정의 (성과, 업무, 데이터, 서비스 요소, 기술 참조 모델)
- 가장 잘 활용되는 참조 모델은 **기술 참조 모델**

‖ 모델 | 특징 |
| **미연방 TRM** | - 프레임워크에서 업무, 서비스, 데이터와의 연관성이 높음¶- TRM 구조가 내부와 외부의 3계층 구조로 되어 있어 대내외 연계 설명이 용이¶- 최신 기술 및 메인프레임의 기술 체계를 폭넓게 수용¶- 지방 주정부 간의 연동을 고려한 접근으로 내부 IT 서비스를 위한 참조 모델로 활용하기에는 다소 어려움 |
| **오픈그룹 TRM** | - 애플리케이션 이식성 지원을 위해 필요한 기반 플랫폼의 구조와 서비스에 중점¶- 상호운용 가능한 기술 환경 구축을 위해 애플리케이션-통신 기반과의 인터페이스를 중시¶- 애플리케이션에 대한 상세한 분류 체계 제공¶- 표준 위주의 이론적 접근으로 플랫폼, 네트워크, 통신 기반은 상세한 서비스 분류가 정의되지 않음 |
| **가트너 TRM** | - 데스크톱 애플리케이션, 엔터프라이즈 애플리케이션 구분¶- 실용적인 분류 체계를 제공하나 상세 분류 기준 미흡 |
| **정보화진흥원 TRM** | - 업무·서비스·데이터 참조 모델 등과 함께 범정부 참조 모델 중 하나로 상호 연계성 기대¶- 컴포넌트 기반 아키텍처 및 서비스 기반 아키텍처 지향¶- 시스템 및 서비스의 상호운용성 보장¶- 국내 정보화 환경을 고려하여 유망하고 안정된 기술 선정 |
- 선진 사례는 기본적인 분류 기준만 제공 — 너무 범용적이거나 특정 영역(정부, 국방 등)에 의존적이라 자사·산업의 기술적 특성을 반영하지 못할 수 있음
#### 다. 참조 모델 구축 방법
- **공통 특성 추출형** : 공통적인 특성을 추출하여 산업군에 맞게 범용적으로 만드는 방식
  - 장점 : 이해하기 쉽고 많은 산출물이 필요하지 않음
  - 단점 : 요소 간 경계가 불명확하고 하위 수준의 정의가 명확하지 않음
- **대표 기업 표본형** : 복잡하고 대표적인 기업을 선정해 그 아키텍처를 표본으로 비슷한 타 기업에서 재활용하는 방식
  - 장점 : 각 산출물의 관계가 정확하고 하위 수준까지 정의됨
  - 단점 : 대부분 공개가 되지 않음
### 2. 참조 모델 사례
- 범정부의 업무, 서비스, 기술, 데이터, 성과 참조 모델
#### 가. 업무 참조 모델
- 특정 기관의 **독립적인 업무 기능을 중심**으로 정의한 참조 모델
- **조직과 무관한 기능 위주의 접근**, 다른 아키텍처를 정의하는 기준으로 활용
- 구성 : 업무 영역 → 업무 단위 → 세부 업무
  - 업무 단위는 특정 기관이 아니라, 어떤 기관이 어떤 목적으로 수행하든 그 업무를 묘사할 수 있는 단위 → 업무 분석의 공통 기준
- 활용 : 기관 간 유사 업무 파악 → 유사 업무 지원 시스템 공동 개발·활용, 다른 기관 프로젝트 중 비슷한 내용 검색·참고
- 분류 체계
  - 정부 : 정책 분야, 정책 영역, 대기능, 중기능, 소기능
  - 일반 기업 : 사업 영역, 업무 영역, 업무 기능
[[img:G1-16]]
#### 나. 서비스 참조 모델
- 업무 수행과 목표 달성을 지원하는 서비스 요소를 분류하기 위한 **기능 중심의 평가 지향적** 참조 모델
- 공공 부문 애플리케이션 서비스의 식별로 업무와 서비스의 연계 및 재사용 촉진, **중복 개발 방지**
- 업무 및 조직에 독립적인 표준 서비스 분류 체계
- 구축 목적
  - 응용 서비스의 재활용을 촉진하기 위한 서비스 분류 체계 제공
  - 정부 기관 업무 지원 컴포넌트에 대한 단일화·통합된 분류 체계 제공
  - 업계와 정부 간 컴포넌트 개발, 축적, 유통의 활성화 촉진
  - 복잡·다양한 부처 응용 서비스를 용이하게 식별
- 구성 : 서비스 영역 → 서비스 유형 → 서비스 컴포넌트
[[img:G1-17]]
#### 다. 기술 참조 모델
- 업무와 서비스 구성 요소의 전달·교환·구축을 지원하는 **표준, 명세, 기술 요소**를 기술하기 위한 것
- 응용 기능 구현에 필요한 정보 기술 및 표준을 분류·정의한 체계
  - 전체 정보 기술을 식별·정의하고 기술 표준과 동향을 관리하여 공통의 정보 기술 기반 수립, 정보 기술 표준화
- 기대 : 기술 및 응용 서비스 재사용 제고, 안전한 교환·전달 기반 환경 구축, 상호 운용성 확보, 정보 기술 성능과 투자 최적화
- 구성 : 핵심 서비스 영역 → 하위 서비스 범주나 기술 표준
  - 서비스 컴포넌트와 연관을 가지며, 정보시스템 간 **상호운용성 증대를 위한 기술 표준을 강조**한 구조
- 다양한 산업군·기업에 바로 적용할 수 있어 구축이 용이하고 기대 효과가 커서 **가장 먼저 적용 가능한 영역**
- 활용
  - 시스템 구축 시 사용할 기술의 표준 프로파일 분류
  - 시스템 관리 시 정보 자산 분류
  - 시스템 통합 시 정보시스템 간 유사성 판단 기준 항목
[[img:G1-18]]
#### 라. 데이터 참조 모델
[[img:G1-19]]
- 기관 간의 **공통 정보 파악과 활용**을 지원하기 위한 모델
- 기관 간 정보 공유 및 데이터의 표준화, 재사용을 지원하기 위한 범정부 데이터 분류, 데이터 표준화와 관리의 기준과 체계를 정의
- 데이터 참조 모델 프레임워크 : 데이터의 표준화, 참조, 재사용에 필요한 구성 요소와 관계를 정의 — **5개 요소**
  - **범정부 데이터 모델** : 범정부에서 구축·활용하는 데이터를 식별하고 데이터 영역 간 관계를 도식화 → 개별 기관은 범정부에 어떤 데이터가 있는지 확인 가능
  - **데이터 분류** : 데이터 분류 기준 정의. 범정부 데이터 모델의 데이터는 분류에 따라 그룹핑되고, 데이터 구조의 데이터 요소는 분류 체계에 매핑 → 관리·검색 용이
  - **데이터 구조** : 범위 내 모든 데이터 요소와 소유주, 표준화 항목 정의, 요소 간 관계 및 정보 저장. 표준화 항목과 가이드를 제시하고 표준 데이터 요소를 등록하여 공유·재사용
  - **데이터 교환** : 교환 대상 정의 및 메시지 구조, 메시지 방식 제시, 교환 내역 관리. 데이터 교환 패키지로 데이터 요소를 참조·재사용
  - **데이터 관리** : 데이터 품질, 표준화, 보안 등의 유지를 위한 관리 정책 및 규칙, 프로세스, 조직 구조 정의
[[img:G1-20]]
#### 마. 성과 참조 모델
- 정보화 성과 관리를 위한 구성 요소와 관계를 정의, 정보화 성과 제고 및 사업 품질 향상을 위한 기본 틀
- 효과
  - 정보화 사업의 성과 정보 생성 지원 → 의사결정 향상
  - 입력, 과정, 출력, 최종 성과 간 **인과 관계**를 명확히 하여 계층별 성과의 연계 증진
  - 성과를 가시화·측정·통제·관리 → 개선 가능성 파악, 성과 증진
- 구성
  - **평가 분류 체계** : 표준화된 평가 지표 개발 및 성과 관리를 위한 기본 틀(분류 체계 및 지표 사례) — 평가 영역, 평가 항목, 평가 그룹, 평가 지표
  - **표준 가시 경로** : 평가 그룹 및 평가 지표 간 관계를 도식화 — IT 성과가 서비스 품질, 고객 만족 등의 업무 성과에 기여하는 과정 파악
  - **성과 관리 표준 양식** : 공공 기관에서 성과 참조 모델을 활용해 평가 및 성과 관리를 하기 위한 표준 양식

### 3. 참조 모델 활용

- 다만 **기술 참조 모델**은 기업 전체 기술 환경을 이해하는 논리적 틀로서, 기술 아키텍처의 현황 진단과 목표 아키텍처 정의 작업의 분류 체계로 잘 활용됨

## 제4절 전사아키텍처 프로세스
### 1. 전사아키텍처 프로세스 개요
- 전사아키텍처를 **구축하고 관리하는 전체 절차** — 작업의 단계와 공정, 작업 내용 등을 정의
- 일반화된 방법론이 있지만 기업의 목적에 맞게 조정 가능
- 전사아키텍처 프레임워크의 구성 요소이기도 하며, 프레임워크 내 다른 구성 요소를 정의하기 위한 모든 절차와 작업을 포함
### 2. 전사아키텍처 프로세스 구성
- 4단계 : **비전 수립 → 구축 → 관리 → 활용**
[[img:G1-22]]
- **비전 수립** : 전사아키텍처 환경을 분석하고, 기업이 추구해야 할 전사아키텍처의 방향 수립
- **구축** : 정보를 어떻게 구성할 것인가를 정의하고 현행 아키텍처와 목표 아키텍처 구축
- **관리 정의** : 효과적인 관리·활용을 위한 관리 체계 정립, 관리 시스템 구축
- **활용 정의** : 목표 아키텍처 달성을 위한 중장기 계획 수립, 전사아키텍처 정보를 IT 관리 프로세스 전반에 활용하는 체계 정의

# 제2장 전사아키텍처 구축
## 제1절 전사아키텍처 방향 수립
### 1. 전사아키텍처 방향 수립 개요
- 전사아키텍처 구축의 **목적**, 지향할 **목표 이미지**, 이를 달성하기 위한 **프레임워크**를 정의하는 것
- 초기에 방향성을 정립하여 이해관계자에게 공동의 목표와 목적 제공
  → 추진 과정의 의견 충돌을 사전에 방지, 이견 발생 시 정의된 목표와 지향점을 상기하며 타협점을 쉽게 찾음
- 아키텍처가 경영 환경과 경영 전략에 능동적으로 대응·발전하도록 **전사아키텍처 변화 동인**을 분석하는 과정
  - 비즈니스 환경 변화 요인을 아키텍처 변화 요인의 시사점으로 도출하여 반영
- 구성 : **전사아키텍처 환경 분석 → 구축 방향 정의 → 프레임워크 정의**
### 2. 전사아키텍처 환경 분석
- 기업의 외부·내부 환경을 분석하고, 이해관계자로부터 전사아키텍처 수립 요건을 도출하는 것
  - 고객, 외부 환경, 경쟁자, 기업의 내부 현황 등 환경 요인 분석
  - 여러 계층 사용자의 기대사항을 도출하여 구축 요건으로 정리
  - 현행 IT 현황을 파악하고 문제점과 개선 사항 정리
- **전사의 범위를 명확히 설정**하는 것도 이 단계에 포함
- 수행 과제
  - 비즈니스 내/외부 환경 분석
  - IT 내/외부 환경 분석
  - 전사 범위 정의

### 3. 전사아키텍처 구축 방향 정의
#### 가. 목적 및 범위 정의
- 일반적 목적과 환경 분석 결과를 기반으로 **구축 목적**을 정의하고, 이해와 관리 역량을 고려하여 **구축 범위**를 정의
  - 지향 가치, 도입 목적의 근거, 목적 달성 시 추구하는 효과 등을 정의
- 전사아키텍처 목적의 예
  - 상호운용성 증대
  - 정보화 투자 의사결정 체계 구축
  - 비즈니스 변화에 대한 신속한 대응 체계 구축
  - 전사적 정보화 표준 정립
  - 고객 지향의 정보화 체계 구축
- 대상 범위 정의 : 전사의 범위와 기업의 현실적 제약 사항을 반영
  - 기업의 미션과 업무 범위 확인 → 필요한 정보화 영역 식별 → 업무 지원 정도 분석 → 대상 영역 정의
#### 나. 전사아키텍처 비전 수립
- 전사아키텍처를 통해 실현하고자 하는 **미래의 모습**과 이를 위해 기업이 **공유해야 할 가치**를 포함
- 이해관계자에게 명확한 도입 방향성을 제공하여 궁극적 목표를 달성하도록 함
- 기업의 목표와 전사아키텍처가 제공할 가치를 일치시켜 **기업 방향과 정보화 방향 사이의 연결 고리** 구축
- 구성 요소
  - **핵심 목표** : 도입을 통해 궁극적으로 달성하고자 하는 기업의 목표 또는 실현하고자 하는 모습
  - **핵심 가치** : 핵심 목표 달성을 위해 구성원들이 추구하거나 지켜야 하는 신념

## 제2절 전사아키텍처 정보 구성 정의
### 1. 전사아키텍처 정보 구성 개요
- 전사아키텍처 정보 : 기업을 잘 이해하기 위해 필요한 업무와 정보기술에 대한 정보로서 **활용 가치가 있고 관리가 용이한 정보**
  - 업무와 정보기술의 구성 요소와 구성 요소 간의 관계를 포함
- 가능한 한 **변하지 않는 구성 요소**를 도출하여 정의하는 것이 이상적
- **관리 비용 대비 효과** 고려 — 활용 이익보다 관리 비용이 크다면 관리하는 의미가 없음
  - 기업 상황을 판단해 현실적으로 관리 가능한 정보를 식별한 후 구축
- 산출물과 구성 요소를 분류하여 매트릭스 형태로 작성 = **아키텍처 매트릭스** → 업무와 정보기술을 통합적으로 보고 전체를 이해
### 2. 아키텍처 매트릭스 정의
#### 가. 아키텍처 매트릭스 개념
- 전사아키텍처 프레임워크의 **핵심 구성 요소**, 전사를 설명하는 모델과 원칙 정보를 통일된 시각으로 볼 수 있는 논리적 틀
- 프레임워크가 계획·실행·운영에 필요한 모든 구성 요소와 관계를 포함한다면, 매트릭스는 **협의의 프레임워크** — 아키텍처 도메인의 산출물을 식별·정의하기 위한 논리적 체계
#### 나. 아키텍처 매트릭스 구성
- **의사결정 유형(관점)**과 **아키텍처 정보 유형(뷰)**의 두 축으로 이루어진 2차원 매트릭스
  - 아키텍처 정보의 활용 방안을 토대로 각 항목에 필요한 산출물을 도출하여 정의
- **의사결정 유형**
  - 조직의 의사결정 유형을 계층적으로 구분 — 업무의 의사결정 특성에 따라 단계 정의
  - 업무와 IT 조직의 이해관계자를 식별하고, 정보화 의사결정 계층 구조를 분석하여 정의
  - 목적에 따라 **3~5단계**로 나눔 — 정보의 관리 수준과 범위에 영향
  - 단계가 많을수록 상세한 정보가 관리되며 구축·관리 **비용**에도 영향
[[img:G1-25]]
- **아키텍처 정보 유형**
  - 특성이 비슷한 아키텍처 정보를 그룹화한 것 — 기업이 관리하는 모든 아키텍처 정보를 수집·분류
  - 업무 영역(조직, 사업 영역, 업무 기능, 업무 프로세스 등)과 정보기술 영역(데이터, 애플리케이션, 기술 인프라 등)
  - 흔히 **업무, 데이터, 애플리케이션, 기술**로 나눔
- 구성 요소 결정 방법
  - 의사결정 유형 : 정보화 관련 의사결정 계층 구조를 **업무 분장, 전결 규정, 면담** 등으로 파악하고, 의사결정 범위·주기·간격에 따라 이해관계자별 계층 구조 정의
  - 아키텍처 정보 유형 : 선진 사례의 뷰 구성을 바탕으로 기업의 정보 관리 요건을 반영하여 조직 간 조정과 합의로 결정

- 선진 사례를 무조건 도입하기보다 참조하되, 기업 현황을 고려하여 **목표 달성에 필요한 구조**로 정의
#### 다. 산출물 정의
- 매트릭스의 각 셀에 필요한 산출물 정의
- 산출물 정의는 **사용 방법론**과 기업의 업무 특성이나 문화에 좌우됨
- 정보통신부와 전산원이 발표한 매트릭스와 표준 산출물 예는 하나의 가이드일 뿐 반드시 따라야 하는 것은 아님

#### 라. 전사아키텍처 정보 구성요소 정의
- **전사아키텍처 정보 구성요소 식별**
  - 공유 정보로 구축하려면 산출물에 포함된 정보를 **중복 없이, 상호 관계가 유기적으로 연결**되도록 구성 요소 정의
  - 문서로만 관리하면 불필요하지만, **데이터베이스로 구축하여 지속 갱신**하려면 산출물을 구성 요소 단위로 분류하고 관계를 명확히 해야 함
[[img:G1-27]]
  - 식별된 구성 요소는 산출물의 종류와 다른 형태
  - **구성 요소 = 정보를 구성하는 기초 단위**, **산출물 = 여러 구성 요소로부터 도출된 복합적인 정보**
- **전사아키텍처 정보 구성요소 연관관계**
  - 연관관계를 통해 특정 업무를 지원하는 시스템, 특정 시스템과 연계된 시스템 등을 알 수 있음
  - 업무 변화 시 영향 받는 시스템, 데이터, 서버 등 파악, 장애 발생 시 연계 시스템을 파악하여 원인 추적 용이
  - 다양한 **연관관계 매트릭스**를 정의하고 보고서·분석 자료 생성
  - 연관관계가 많을수록 활용 가치가 높지만, **유지관리 비용**을 감안하여 현실적인 수준에서 관리
#### 마. 아키텍처 매트릭스 정의 시 고려사항
- 첫째, 산출물은 업무와 IT, 관리자와 실무자 사이의 중요한 **커뮤니케이션 툴** — 모든 계층의 사람이 산출물이 범위와 목적에 적합하다고 확신할 수 있어야 함
- 둘째, 조직적·정치적·지리적 특성, 조직의 편견 등 **조직 문화와 의사결정 구조**가 반영되어야 함 — 같은 정보라도 산출물이 정의되는 셀이 달라질 수 있음
- 셋째, 아키텍처 개발 표준에 대한 **준수성**을 높이고 조직별로 **통일된 접근**이 가능하도록 정의 — IT 조직의 성숙도를 고려, 서로 다른 개발 환경과 요건을 반영하면서 통일성과 일관성 유지
- 넷째, 각 아키텍처 도메인은 상호 간에 **연계성**을 가져야 함 — 비즈니스 아키텍처 산출물이 데이터-애플리케이션-기술 아키텍처에 반영되어 통합적 관리
### 3. 참조 모델 정의
- 기업의 기준 모델로 정의할 참조 모델의 체계와 구조를 정의하고 컨텐츠 구축
- 정부, 지주회사 등 **다수의 전사를 가진 기관은 참조 모델을 정의**하고, **개별 기업은 정의된 참조 모델을 참고하여 구성 요소의 타당성을 확인**
- 참조 모델은 정보화의 통합성, 중복 개발 방지, 공유 정보의 발견, 상호운용성 향상을 목적으로 설계 → 개별 기업은 상위 기관이나 산업별 참조 모델을 참고하여 구성 요소를 정의하는 것이 바람직
- 범위는 산업이나 가치 사슬 네트워크에 따라 다름 — 미션과 비전, 서비스 특성, 기업 간 이해관계 고려
- **기술 참조 모델**은 개별 기업도 기술 환경 변화와 상호운용성을 고려하여 구축 시 정의·활용하는 것이 바람직
### 4. 전사아키텍처 원칙 수립
- 전사아키텍처 비전 달성을 위해 **구성원들이 공통적으로 지켜야 하는 규범** 정의
- 목표 달성을 위한 **의사결정의 객관적 기준** 제시 → 의사결정 지원, 업무 협조·조정을 위한 의사소통의 투명성 제공
- 비즈니스 전략과 정보화 전략의 연결성 강화, 개별 의사결정을 조직 목표에 정렬
- 원칙의 구성 요소
  - **원칙** : 원칙의 내용을 간략하게 기술
  - **의미** : 원칙이 가지는 의미 설명
  - **근거** : 원칙으로 채택된 원인 또는 배경
  - **기대효과** : 전사아키텍처 수립에 미치는 영향 또는 준수 시의 기대효과
- **기본 원칙**과 **아키텍처별 원칙**으로 구분
  - 기본 원칙 : 전사적 차원의 대원칙, 아키텍처별 원칙의 근거 — **방향 수립 단계**에서 정의
  - 아키텍처별 원칙 : **정보 구성 정의 단계**에서 아키텍처 매트릭스가 결정된 후 도메인별로 정의
[[img:G1-28]]
- 아키텍처 원칙은 기본 원칙을 기반으로 비즈니스, 데이터, 애플리케이션, 기술 아키텍처 도메인별로 정의 — 각 아키텍처 정보 정의·관리의 기준, 구축 시 준수되어야 함
[[img:G1-29]]
[[img:G1-30]]
- 원칙 수립 시 고려 사항
  - 원칙의 **의도가 명확**하게 제시되어 적용 시 혼돈을 최소화
  - 아키텍처 및 계획 수립 관련 의사결정을 효율적으로 가이드
  - 중대한 정보 기술 관련 의사결정 시 **규범**으로 활용
  - 정보 관리 및 기술 관련 모든 의사결정은 전사아키텍처 원칙을 기반으로 수행
  - 원칙 간 **상반되는 지향점**을 갖지 않도록 용어를 주의하여 선택
## 제3절 전사아키텍처 정보 구축
### 1. 전사아키텍처 정보 구축 준비
#### 가. 자료 수집
- 우선 기존에 작성된 자료 수집 — 수집 자료는 정의된 아키텍처 매트릭스에 따라 달라짐
  - 업무 : 업무 지침서나 규정 등
  - 데이터·애플리케이션 : 정보시스템 구축 시 작성한 산출물이나 완료 보고서 등
  - 기술 인프라 : 시스템 도입 관련 문서와 운영 매뉴얼 등
- 정의된 산출물 형식 그대로의 자료가 없으면 유사 산출물을 활용하거나 생성·보완
#### 나. 전사아키텍처 정보 구축 방식
- **상향식** : 최하위 구성 요소를 조사·분석하여 공통점을 파악하고 모아 상위 구성 요소를 정의해 나가는 방식
  - 장점 : 조직의 **모든 업무가 포함**되는 것을 보장
  - 단점 : 상위 업무 기능 분류의 **수준이 서로 다르게** 나타날 수 있음
- **하향식** : 최상위 구성 요소부터 분류 기준에 따라 하위 구성 요소를 도출하는 방식
  - 장점 : 일반적·목적에 따른 분류 기준을 따르므로 **관점이 명확**
  - 단점 : 일부 업무가 **누락**될 수 있고, 어디에도 포함되지 않는 구성 요소가 발생할 수 있음
### 2. 현행 아키텍처 정보 구축
- 현재 업무나 정보시스템에 대해 기존 자료를 분석하여 정보를 구축
- 상위 수준의 업무 기능과 시스템 분류를 우선 수행한 후 그 기준에 따라 나머지 정보를 구축하는 것이 효율적 — 상위 분류 기준이 정리되면 나머지는 **병렬**로 수행 가능
- 현행 아키텍처는 **아키텍처 매트릭스의 전 범위**에 걸쳐 수행하는 것이 바람직 — 각 셀의 산출물 기준으로 현재 모델·문서를 정리·보완하여 현행화
#### 가. 현행 비즈니스 아키텍처 정보 구축
- 기업의 비전, 경영 목표, 조직 구조 등을 파악하여 정의하는 것에서 시작
- 업무 기능 정의
  - 하향식(Top-Down) : **가치 사슬 분석**으로 최상위 업무 기능을 도출하고 점점 세분화
  - 상향식(Bottom-Up) : 현재 수행하는 단위 업무를 조사하고 **유사성** 기준으로 묶어 상위 업무 기능 도출
- 도출된 업무 기능은 비전·조직 구조와 연계성을 파악하고, 애플리케이션·데이터 등과의 연관 관계로 상호 검증
- 업무 프로세스 정의도 같은 방식
- 정의 내역 : 전사 사업 모델 분석, 조직 모델 분석, 업무 기능 모델 정의, 프로세스 모델 정의, 업무 매뉴얼 파악
#### 나. 현행 애플리케이션 아키텍처 정보 구축
- **업무 기능 분류를 기반**으로 전사 애플리케이션을 분류하고 연관 관계를 분석하는 것에서 시작
- 애플리케이션의 구조와 서비스, 응용 기능 등을 도출
- 애플리케이션·서비스와 데이터, 조직·업무 기능 등과의 연관 관계를 분석하여 정합성 검증
- 애플리케이션 영역이나 구성 요소는 **서비스 참조 모델**을 참조하여 연관 서비스 영역과의 연결성 확인
- 정의 내역 : 전사 애플리케이션 영역 식별, 애플리케이션 모델 정의, 컴포넌트 모델 정의, 프로그램 목록 파악, 애플리케이션 원칙·표준 파악
#### 다. 현행 데이터아키텍처 정보 구축
- 하향식 : 업무 수행에 필요한 데이터 요건을 식별하여 데이터 모델로 표현
  - 의사결정이나 현황 파악의 정보 요건을 바탕으로 필요 데이터를 도출하고, 정보 요건을 상세화하면서 세부 모델 정의
- 상향식 : 각 시스템에서 사용하는 데이터 정보를 분석하여 데이터 모델로 정렬·표현
  - 운영 중인 데이터베이스의 물리 테이블에 대응되는 논리 개체와 관계를 정의하고, 논리 개체를 주제별로 묶어 개념 개체와 관계 정의
- **계획자 수준의 상위 정보만 구축 → 하향식**, **실무자 수준의 정보 구축 → 상향식**이 적합
- 구축 후 업무 기능, 애플리케이션과의 연계성 분석으로 정확성 검증
- 정의 내역 : 전사 데이터 영역 식별, 개념·논리·물리 데이터 모델 정의, 데이터베이스 객체 파악, 데이터 원칙·표준·관리 프로세스 파악
#### 라. 현행 기술 아키텍처 정보 구축
- 전산 장비, 시스템 소프트웨어, 네트워크 등 **기술 인프라의 구성**을 체계적으로 분류하여 표현
- 기술 인프라 영역 분류 → 영역별 구성 요소 도출 → 구성 요소 간 관계 식별·표현
- **기술 참조 모델을 사전에 정의**하여 참조하면 전체적인 일관성 확보
- 정의 내역 : 전사 기술 영역 식별, 기술 참조 모델 정의, 기술 표준 분석, 기술 아키텍처 요소 식별, 기술 자원 목록·제품 목록 파악
### 3. 목표 아키텍처 정보 구축
- 현행 아키텍처의 **문제점과 개선 사항**을 도출하여 목표 아키텍처에 반영하는 방식
- 정의 순서 : **비즈니스아키텍처를 먼저** 정의하고, 이를 효율적으로 지원하는 아키텍처를 정의
- 범위는 목적에 따라 다르지만, 일반적으로 초기 수립 시에는 현행과 달리 **아키텍처 매트릭스의 개념적 수준까지** 정의
  - 개념적 수준 이하의 산출물은 실제 시스템 구축 단계에서 수행하는 것이 일반적
  - 비즈니스와 기술 환경 변화에 대한 **유연성** 확보 의미도 있음
#### 가. 목표 비즈니스아키텍처 구축
- 현행 추가 업무와 개선 요구 사항 반영, 사전에 **BPR(업무 프로세스 재설계)** 등이 이루어졌으면 그 결과 반영
- **업무 참조 모델**과의 연계성을 파악하여 관계 확인
- 목표 비즈니스아키텍처의 수준에 따라 데이터 및 애플리케이션아키텍처 수준이 결정됨
  - 기업의 미래 비전 달성을 위한 모습을 정의하며, **다른 아키텍처의 적합성을 판단하는 중요한 기준**
- 정의 내역 : 전사 사업 모델, 조직 모델, 업무 기능 모델, 프로세스 모델 정의, 업무 매뉴얼 정보 구축
#### 나. 목표 애플리케이션 아키텍처 정보 구축
- 목표 비즈니스 아키텍처를 지원하는 전사 애플리케이션의 구조 정의
- 목표 업무의 개선 요구, 추가 애플리케이션 구축 요구, 애플리케이션 자체의 개선 요구를 반영
- 비즈니스·데이터아키텍처와 연관 관계를 비교하여 검증
- **서비스 참조 모델**과의 연계성을 파악하여 상위 기업이나 유관 기업과의 인터페이스 제고
- 정의 내역 : 전사 애플리케이션 영역 모델, 애플리케이션 모델, 컴포넌트 모델 정의, 프로그램 목록 정보 구축
#### 다. 목표 데이터아키텍처 정보 구축
- 목표 비즈니스 아키텍처를 지원하는 데이터를 식별하여 모델로 표현
- 목표 업무의 개선 요구, 추가 데이터 요구, 데이터 자체의 개선 요구를 반영
- 비즈니스·애플리케이션 아키텍처와 연관 관계를 비교하여 검증
- **데이터 참조 모델**과의 연계성을 파악하여 상위 기업이나 유관 기업과의 데이터 인터페이스 제고
- 정의 내역 : 전사 데이터 영역 모델, 개념·논리·물리 데이터 모델 정의, 데이터베이스 개체 정보 구축, 데이터 원칙·표준·관리 프로세스 정의
#### 라. 목표 기술 아키텍처 정보 구축
- 목표 애플리케이션·데이터아키텍처를 잘 지원할 수 있는 기술 아키텍처 정의 — 최근 기술 추이와 기업 특성 고려
- **기술 참조 모델과 연계**하여 전체 기술 인프라의 상호운용성 제고 — 기술 참조 모델을 바탕으로 기술 구성 요소와 기술 분야를 상세화
- **표준 프로파일**
  - 조직 수준에 따라 선택되는 표준의 기준, 수량, 깊이가 다름
  - 동일 기업 내 표준은 그 기업의 표준 프로파일과 **일관성**을 가져야 함
  - 표준 선정 시 **개방형 시스템**의 구현과 **국제 표준**을 항상 고려
  - 표준 프로파일이 개방 시스템 환경을 보장하지는 않으므로, 개방형 시스템 구축 기준을 추가로 정의
  - 관리 가능한 수준으로 구성하고, 기술 발전·환경·비전·업무에 따라 계속 갱신
- 정의 내역 : 전사 기술 영역 모델, 기술 참조 모델, 표준 프로파일, 기술 아키텍처 모델 정의, 기술 자원 목록·제품 목록 정보 구축
# 제3장 전사아키텍처 관리 및 활용
## 제1절 전사아키텍처 관리 체계
### 1. 전사아키텍처 관리 체계 개요
#### 가. 전사아키텍처 관리 체계 개념
- 정보를 정확하게 구축하는 것보다 더 중요한 것은 **정보를 관리하고 활용할 수 있는 체계를 정립**하는 것
- 전사아키텍처 관리 체계 : 전사아키텍처를 유지 관리하기 위한 **조직과 프로세스 측면의 기반**을 구축하는 것
- 목적 : IT 기획에서 서비스 제공에 이르는 모든 과정에서 전사아키텍처 정보를 활용해 의사결정 → **일관성과 합리성 증대**
- 구성 : **관리 조직, 관리 프로세스, 관리 인력**
- **IT 관리 체계와 전사아키텍처 관리 체계**
  - IT 관리 체계('IT 거버넌스') : IT 관리의 효율성과 효과성 증대를 위한 IT 전반의 관리 체계 정립
  - 전사아키텍처 관리 체계('EA 거버넌스') : 전사아키텍처를 유지하고 지속적으로 개선하기 위한 제도적 기반 구축
  - 전사아키텍처 관리 체계는 **IT 관리 체계의 틀 속에서 통합**되어야 함
[[img:G1-31]]
> **[Tip] 전사아키텍처 관리 체계와 EA 거버넌스**
> 전사아키텍처 관리 체계를 최근 EA 거버넌스라는 용어로 자주 사용함. 이 책에서는 동일한 의미로 보며, IT 관리 체계와 IT 거버넌스도 같은 의미로 봄
#### 나. 전사아키텍처 관리 체계 구축 방향
- 효과를 높이려면 **전사아키텍처 간의 통합성**과 **전사아키텍처 내의 통합성** 확보
  - 전사아키텍처 간 통합성 : 복수 기관 간에 통합적으로 구축
  - 전사아키텍처 내 통합성 : 단일 기업 내 영역 간에 통합적으로 구축
- 정착을 위해 **장기적 접근** — 단기 효과보다 장기간의 효과 중시
- IT 조직만의 노력으로는 달성할 수 없음 → **전사적인 추진 체계**
  - 현업 부서도 전사아키텍처를 이해하고 비즈니스 아키텍처 정보를 활용하며 IT 혁신에 의견 제시·협조
- 효과적인 관리 체계 구축을 위한 고려 사항
  - 조직 체계, 프로세스 체계 등을 **문서화하여 제도화**
  - 이해당사자의 인지도 향상과 정보 활용도 증진을 위한 **교육 프로그램** 제공
  - 목표 아키텍처로의 전환, 정보자원 관리 혁신 등 도입에 따른 **변화 관리** 종합 프로그램 운영
  - 관리 체계를 **주기적으로 점검**하여 개선점을 반영하는 제도적 장치 마련
  - 관리 시스템의 활용도와 만족도를 주기적으로 점검하여 시스템 품질 지속 개선
### 2. 전사아키텍처 관리 조직 체계
#### 가. 전사아키텍처 관리 조직 개요
- 전사아키텍처 관리를 위해 필요한 **직무와 직무 간의 관계, 업무 분장**을 정립하는 것
- 기업 전체 또는 정보관리 전체 조직과 **일관성** 확보
- 계획자 수준에서 실무자 수준까지 다양한 시각에서 책임과 역할 정의
- 직무 예
  - **전사아키텍처 담당 임원** : 수립에 대한 투자 의사결정, 주요 추진 과정 승인, 전사적 지원 확보
  - **전사아키텍처 아키텍트** : 전체적 원칙 및 방향 정의, 관리 총괄, 영역 간 조정
  - **영역별 담당자** : 비즈니스·데이터·애플리케이션·기술아키텍처 등 영역별 원칙과 정보 관리
  - **관리 시스템 관리자** : 관리 시스템의 구축 및 운영
  - **추진 위원회** : 수립 및 적용에 대한 전사적 중요 의사결정의 승인 또는 자문
#### 나. 전사아키텍처 관리 조직의 정의
- **전담 조직이 없다면 전사아키텍처 정보는 하나의 문서에 불과** — 상호 연관성을 유지하며 지속적으로 관리되어야 함
- 선진 사례를 참고하고, 정보 관리 전체 조직과 관리 조직의 문제점을 파악해 개선 방향을 도출하여 정의
- 조직 구성 예의 공통 특징 : 정보 관리를 위한 **위원회 및 전담 조직을 아키텍처 영역별로** 정의, 이슈를 팀 안에서만이 아니라 **공론화된 회의**로 해결
[[img:G1-32]]
- 조직 정의 시 고려 사항
  - **IT 조직의 규모**
    - 별도 조직을 둘 수 없는 중소 규모 : 관리 **운영위원회(또는 TFT)** 중심으로 정의하고 전담 인력 양성
    - 별도 조직을 둘 수 있는 대규모 : **전담 조직을 신설**하고 운영위원회로 전사적 의사결정 공유
  - **전사아키텍처 구축의 목적**
    - 아키텍처 관리와 IT 표준화가 목적 : 전사아키텍처와 **IT 표준을 통합 관리**하는 조직 정의
    - 신시스템 구축 계획 수립이 목적 : 프로젝트 기간 중 정보를 관리할 조직 필요 — **PMO**와 관리 전담 조직 정의
  - **IT 조직과 현업과의 관계**
    - 의사소통 문제가 있으면 현업의 요건을 종합적으로 관리하는 조직을 추가 정의
### 3. 전사아키텍처 관리 프로세스
#### 가. 전사아키텍처 관리 프로세스 개요
- 전사아키텍처를 관리하기 위한 **활동**을 정의하는 것
- 관련 모든 활동을 포함하고, 전체 정보관리 업무 체계와 **일관성** 확보
- 세부 업무의 분류·내용 정의뿐 아니라 준수 규정, 표준화된 수행 절차, 문서 양식 정의 포함
- 구분 예
  - **전사아키텍처 기획** : 관리 방향과 효과적 적용·활용 계획 수립 등 기획 관련 제반 활동
  - **전사아키텍처 변경 관리** : 정보 변경의 검토, 승인, 변경 이행 등 **정보의 최신성과 품질** 확보 활동
  - **전사아키텍처 준수 통제** : 정보관리 부문이나 현업 부서가 전사아키텍처 정보를 참조·준수하는지 점검·지원
  - **전사아키텍처 활용 지원** : 정보의 공지, 홍보, 교육, 활용 사례 전파 등 활용도 제고 활동
  - **전사아키텍처 관리 시스템 관리** : 관리·활용 효율성 제고를 위한 시스템 구축·운영 활동
  - **전사아키텍처 평가** : 평가 모형을 정의하고 주기적으로 평가하여 개선 기회 식별
#### 나. 전사아키텍처 관리 프로세스 구성
- 일반적 흐름 : 구축 → 활용·통제 → 환경 변화와 활용 상태 평가 → 변경 조치 → 다시 정보로 구축되어 전사적으로 적용
[[img:G1-33]]
- 모든 활동이 **전사아키텍처 중심**으로 수행되도록 정의
  - 기존 IT 프로세스에 변경·관리 프로세스만 신규로 추가하면, 기존 프로세스에 밀려 제대로 수행되지 않을 가능성이 큼
  - 그 결과 **정보의 최신성**을 유지할 수 없고, 원칙이 IT 활동에 적용되지 않아 **정보의 완전성**을 유지할 수 없음
- 따라서 IT 프로세스의 **수립-활용/통제-평가-변경** 흐름을 전사아키텍처 관점에서 식별하여 정보 중심으로 설계 → 완전성 유지
- 정보 변경을 개발 및 운영 프로세스에서 식별하여 곧바로 정보 변경으로 이어지게 함 → 최신성 유지
[[img:G1-34]]
### 4. 전사아키텍처 관리 인력
#### 가. 전사아키텍처 관리 인력 개요
- 관리 직무별 **역량을 정의**하고 이를 **확보하기 위한 방안**을 정의하는 것
  - 역량 요소 분류 → 직무별 할당 → 교육 계획 수립 → 역량 수준 평가 체계
- 정착과 성과를 위해 관련 인원의 역량 확보가 매우 중요 — 직무별 **맞춤식 교육** 제공
- 역량 요소
  - **리더십 역량** : 사상과 가치의 의미를 정확히 파악하고, 전사적 공감대 형성과 내재화를 위한 변화 관리를 이끄는 관리 능력
  - **기술적 역량** : 구축·관리 절차와 방법론을 이해하고, 정보를 정의하며, 관리 시스템을 구축할 수 있는 기술적 능력
  - **활용 역량** : 정보를 활용하여 정보관리 업무와 현업 업무의 효율성·효과성을 증대하는 실용적 능력 — 투자 성과와 직접적으로 연관
#### 나. 전사아키텍처 전문가 육성
- 관리 조직 정의만으로는 정보를 지속적으로 발전시킬 수 없음 → **아키텍처 영역별 아키텍트가 조직 내부에** 있어야 함
- 구축 프로젝트 참여 내부 인력 중심으로 관리 조직을 구성할 수 있으나, 아키텍트로 발령만 내면 끝나는 것이 아님
  - 관리 직무에 필요한 **기술 수준을 정의**하고, 부족한 기술은 교육으로 쌓도록 관리
[[img:G1-35]]
- 내부 아키텍트의 현재 기술 수준을 평가하여 **인력 양성 계획** 수립
  - 각 아키텍트에게 **경력 개발 경로**를 제시하고 교육 및 평가 과정을 통해 상위 직무로 성장하도록 함
## 제2절 전사아키텍처 관리 시스템
### 1. 전사아키텍처 관리 시스템
#### 가. 전사아키텍처 관리 시스템 개요
- 전사아키텍처 정보를 구축·관리·활용하는 모든 업무 프로세스의 효율성 제고를 지원하는 정보 시스템
- 구분
  - **정보 정의 도구 영역** : 모델링 도구 포함
  - **정보 관리 영역** : 전사아키텍처 리포지터리(Repository)와 포털
  - **정보 활용 영역**
- **모델링 도구** : 정보를 도식화하여 표현. 아키텍처별 개별 도구일 수도, 통합 도구일 수도 있음
- **리포지터리** : 정보를 저장하는 데이터베이스와 정보 데이터 관리 포함
- **포털** : 다양한 사용자가 쉽게 접근할 수 있도록 사용자 인터페이스 제공
- 경우에 따라 정보를 전문적으로 분석·활용하는 도구 포함
[[img:G1-36]]
### 2. 전사아키텍처 정보 정의 도구
- 업무, 데이터, 애플리케이션, 기술아키텍처 정보를 도식화하여 표현하는 모델링 도구
  - 전용 EA 모델링 도구, 범용 데이터·애플리케이션 모델링 도구, 경우에 따라 일반 문서화 도구도 가능
- 모델링 도구로 등록하는 이유 : 정보의 **활용도**를 높이기 위함
- 관점과 뷰 간의 **관계 정보까지 관리**되어 상호운용성과 통합성 효과를 내려면 EA 모델링 도구 사용이 바람직
- 필요 기능
  - 각종 다이어그램 표현, 프레임워크 생성, 개체 간 관계 표현
  - 모델링 정보에 대한 질의와 보고서 생성
  - 전사아키텍처 포털로의 정보 인터페이스
### 3. 전사아키텍처 정보 관리 시스템
- 구성 : 정보를 저장하는 **리포지터리**, 사용자에게 배포하는 **포털**, 전문적 분석을 위한 추가 도구
[[img:G1-37]]
- 기능 : 정보의 **버전 관리**, 현행과 목표의 비교, 아키텍처 매트릭스·참조 모델과의 연계, 사용자 권한 관리, 활용 통계, 분석 및 의사결정 지원
- 도입 방법 : **패키지 도입 후 커스터마이징** 또는 **자체 구축** — 일반적인 패키지 도입과 자체 개발의 차이 관점에서 장단점 비교
- 효과
  - 유지 관리 효율성 극대화, 정보 공유와 변경 관리에 편리한 정보 접근성 제공
  - 업무와 IT의 연관 관계 분석 및 차이 분석 용이
  - 아키텍처 매트릭스 기반 정보 제공으로 IT 담당자 간 일관되고 일원화된 의사소통
  - 결국 **IT 투자의 중복성 제거 및 IT 자원의 재활용성 극대화**
- 도입 효과 세 가지
  - 첫째, **정보 공유** : 이해관계자가 각 아키텍처 요소를 정확하게 파악, 담당자 관점에 맞는 최신 정보 제공, 다수 사용자에게 동일 정보 제공, 다양한 조회 기능으로 빠른 접근
  - 둘째, **의사소통 도구** : 현업과 IT가 공유할 수 있는 모델을 제공하여 의사소통 오류 감소, 요소 간 연관 관계 파악으로 문제를 사전에 인식 → 현업 만족도 향상
  - 셋째, **의사결정 도구** : 업무와 IT 서비스 간 차이 분석, 현행과 목표 아키텍처 간 차이 분석을 손쉽게 하여 시스템 개선 관련 의사결정이 빨라짐
## 제3절 전사아키텍처 활용
### 1. 전사아키텍처 활용 개요
- 신규 IT 투자는 계속되고 기존 시스템의 유지보수 비용은 계속 증가
- 전사적 아키텍처와 원칙 없이 단위 업무 위주의 근시안적 IT 투자가 계속되면 → **중복 개발, 상호운용성 저하** → 재구축·재투자 반복, 변화에 대응 불가
- 활용 활성화를 위해 정보가 **IT 관리 업무에 실질적으로 활용**되어야 함
  - 이행 계획 수립, 효율적인 IT 투자 의사결정과 IT 자원 관리
- 활용 영역 두 가지
  - **목표 아키텍처 이행 계획** : 수립 후 목표 아키텍처 달성을 위한 이행 계획을 수립하고 프로젝트 추진 — 주로 **새로운 시스템 추진**이 목적인 경우
  - **전사아키텍처 정보 상시 활용** : 정보를 활용하여 **일상의 IT 업무를 지원** — 전반적인 IT 관리 수준 증대가 목적인 경우
### 2. 목표 아키텍처 이행 계획
- 현행에서 목표 아키텍처로의 이행 전략과 구체적인 이행 계획 수립
- **현행과 목표의 차이 분석**으로 프로젝트 정의 → 유사성과 상호 연관성을 고려해 **우선순위** 결정 → 이행 전략과 세부 이행 계획 수립
- 성공적 추진을 위한 **변화 관리 계획** 필요
- 세부 이행 계획 : 필요 인력과 자원의 리소스 계획, 추진 일정, 비용 계획 등
- 주요 활동 및 작업
  - **아키텍처 차이(Gap) 분석** : 목표 및 현행 아키텍처 검토, 차이 분석
  - **프로젝트 정의** : 프로젝트 목록 정의, 프로젝트별 필요 리소스 정의, 우선순위 및 연관성 분석
  - **이행 전략 수립** : 단계별 이행 전략 대안 수립, 전략별 타당성 분석 및 대안 확정
  - **이행 계획 수립** : 프로젝트별 추진 방법 정의, 상세 일정 계획 수립
  - **변화 관리 계획 수립** : 대상 및 변화 요인 식별, 계획 수립, 교육 계획 및 자료 작성
### 3. 전사아키텍처 정보 상시 활용
- 전사아키텍처 정보를 IT 업무 전반에 **일상적으로 활용**하는 것
- 선행 조건 : 정보의 **지속적인 개선 체계**와 **관리 시스템 구축**
- 적용 영역을 적극 발굴하고 업무 적용을 점점 확산
- IT 관리 생명주기(IT 기획 관리, IT 구축 관리, IT 운영 및 통제) 전반에 활용

#### 가. IT 기획 관리
- 중장기·단기 정보화 계획 수립 시 전사아키텍처 정보를 바탕으로 업무와 전략적 방향에 맞는 목표 시스템을 정의하고 추진 계획 수립
  - 추진 계획은 전사아키텍처 정보를 기준으로 **타당성 검증과 승인**
- **IT 포트폴리오 관리**에도 활용
  - 비즈니스 전략, 정보기술 변화, IT 투자 여력 등을 고려하여 사업 영역, 정보시스템 영역, 정보시스템 생명주기별로 적정한 투자가 이루어지도록 IT 투자를 총체적으로 관리
  - 업종 통합, 대형화, 세계화 진전으로 정보 자원의 효율적 배분을 위한 필요성 증대
#### 나. IT 구축 관리
- 분석, 설계, 구축, 이행 등 **시스템 구축 생명주기 동안** 전사아키텍처 정보를 바탕으로 범위 정의, 애플리케이션 설계, 데이터아키텍처 정의, 기술 체계 선정
- 원칙, 표준, 아키텍처, 참조 모델 등을 참조 → 중복 배제, 재사용성·통합성 제고, IT 비용 절약
- 여러 프로젝트가 동시에 진행되고 관리 난이도가 높아져 **전문적·독립적인 프로젝트 관리 기능** 필요
  - 관리의 기준이 먼저 정의되어야 하며, 그 기준이 바로 **전사아키텍처 정보**
  - 프로젝트 변화 관리 측면에서도 큰 활용성
- 시스템 구축 완료 후 **변경 사항을 전사아키텍처 정보에 반영**하는 것이 매우 중요
#### 다. IT 운영 및 통제
- **현행 아키텍처 정보**를 바탕으로 시스템을 운영하고, 개선·추가 요구 발생 시 정보를 바탕으로 수용·적용 방안을 결정하여 시스템 변경에 반영
- 성능 문제나 장애 발생 시 신속한 파악과 해결에 매우 유용
- 시스템 **도입 및 폐기의 근거 자료**, 운영 이슈의 경중을 가리는 정보로 활용
- IT 서비스 품질 지표가 아키텍처 프로세스와 연관되어 주기적인 평가·보완이 이루어지고, 보완 내용이 정보 전략이나 예산 프로세스에 제공
### 4. 전사아키텍처 효과적 활용 방안
- 도입 초기에는 일반적 기대 효과 중심으로 활용되나, 시간이 지나 성숙도가 높아지면 요구 수준이 높아지고 프레임워크나 매트릭스의 변경, 전반적 개선이 필요할 수 있음
- 고려 사항
  - 정보 자체의 **품질 보장** — 현행 및 목표 시스템 상황이 항상 최신 상태로 정확히 반영
  - 정보를 관리하고 적용을 통제하는 **전담 조직** 구성·운영 — 품질과 활용도 제고 책임, 필요 시 근거 자료 제시
  - 정보를 전사적으로 공유·활용할 수 있는 **절차와 시스템**
- 전사아키텍처 도입은 일시적·단편적 개선이 아니라, 정확한 정보를 바탕으로 통합되고 일관성 있게 정보화를 **계획, 실행, 검증 및 평가하는 체계**를 갖추는 것
[[img:G1-38]]
- 구축은 일정 기간의 프로젝트로 수행되지만, 중요한 것은 **정보가 활용되어야 한다는 사실**
  - 활용 목적에 따라 각 아키텍처 도메인을 정확하게 정의하고, 정의된 아키텍처를 유지하기 위해 더 많은 노력
- 지속적인 관리 및 평가 활동을 통해 궁극적인 **IT 혁신** 달성
### 5. 전사아키텍처와 데이터아키텍처 전문가 영역
#### 가. 전사아키텍처와 데이터아키텍처 프레임워크
- 데이터아키텍처 전문가의 영역 = 데이터아키텍처 전반 = **광의의 데이터아키텍처 영역**
  - 데이터아키텍처 원칙, 데이터아키텍처 정보, 데이터아키텍처 관리 포함
[[img:G1-39]]
- 데이터아키텍처 전문가(DAP)는 데이터아키텍처를 정의할 때 **전사아키텍처 정보와 항상 연계**하여 생각
  - 전사아키텍처의 원칙과 정보, 관리 체계를 준수하고 데이터아키텍처 분야에서 더욱 구체화·관리
  - 데이터 부문의 변경 사항이 전사아키텍처 정보에 잘 반영되도록 관심
- 데이터아키텍처 담당자의 임무 : 전사아키텍처 프레임워크를 바탕으로 **데이터아키텍처 프레임워크를 상세화·구체화**
  - 데이터아키텍처 정책 : 데이터아키텍처 매트릭스, 비전, 원칙 및 표준
  - 데이터아키텍처 정보 : 데이터 구조, 데이터 흐름, 데이터 활용, DB 관리, 데이터 품질 — 데이터 관리자의 업무 프로세스와 연계
  - 데이터아키텍처 관리 : 관리 체계, 메타 데이터 관리 시스템, 평가
[[img:G1-40]]
#### 나. 전사아키텍처와 데이터아키텍처
- 데이터아키텍처가 의미 있으려면 **전사아키텍처와 통합**되어야 함
  - 전사아키텍처 전체와 범위가 일치, 타 아키텍처 영역과 연계, 상위·하위 아키텍처 간 연계
[[img:G1-41]]
- 데이터아키텍처가 이루어야 할 3가지 통합성
  - **범위 통합** : 전사아키텍처 범위 전체에 대한 각 모델 내의 불일치성 제거 — 중복 개발의 반대 개념, **IT 투자의 효율성** 제고의 원천
  - **수평 통합** : 관련된 타 영역과의 불일치성 제거 — 운영의 조화, **IT 투자의 효과성** 제고의 원천
  - **수직 통합** : 계획자, 책임자, 설계자, 개발자 간의 불일치성 제거 — 요구 사항의 일치, 정렬(Alignment), **IT 투자의 품질** 제고의 원천
